# 모듈 계약

| 호출하는 쪽 | 받는 쪽 | 호출 |
|---|---|---|
| lily-frontend | lily-builder | `POST /api/builds` (클라우드). 내 PC면 `POST /api/agents/{key}/builds`. 상태는 `GET /api/builds/{id}`. `commit`이 40자면 `builder_runs.commit_sha`에 남긴다 |
| lily-frontend | lily-builder | `POST /api/agents`, `GET /api/agents/{key}` |
| lily-frontend | lily-builder | `GET /api/apps/{app}/address`, `POST /api/apps/{app}/home` 본문 `{ home, migrateDatabase }`(DB 이전은 확인 창에서 고른다), `POST /api/apps/{app}/home/cancel`(주소 전환 전 단계에서만), `GET`·`PUT /api/apps/{app}/burst`(버스팅 켜기·끄기, 클라우드 비율 0~100) |
| lily-frontend | lily-builder | `POST /api/apps/{app}/stop`, `POST /api/apps/{app}/start`, `DELETE /api/apps/{app}?database=` |
| lily-frontend | lily-builder | AWS + GCP 프로젝트: `POST /api/builds` 의 `cloudProvider: MULTI`, `GET`·`PUT /api/apps/{app}/traffic` 본문 `{ gcpPercent }`(0~100, 나머지는 AWS) |
| lily-builder | lily-cicd | `POST /api/deployments`. 대기 배포는 `aliases`(`{app}-cloud.lilycloud.kr`)를 같이 보낸다. DB가 내 PC나 기존 DB면 역방향 터널 주소로 만든 `databaseEnv`를 보내고, 그때 cicd는 provisioner를 부르지 않는다. `database`와 같이 보내면 400 |
| lily-builder | lily-cicd (GCP·AWS) | 앱의 클라우드(`cloudProvider`)에 맞는 cicd 로 보낸다. AWS + GCP 앱은 GCP 에 일반 배포(`aliases: [{app}-gcp]`) 뒤 AWS 에 `databaseEnv`(호스트 `db-relay-gcp`) + `followPgroll: true` + `aliases: [{app}-aws]`. 롤백은 AWS → GCP, 삭제는 AWS(`database=false`) → GCP |
| lily-builder | lily-cicd | `GET /api/deployments/{app}/progress`, `GET /api/apps/{app}`, `PUT /api/apps/{app}/replicas`, `POST /api/deployments/{app}/rollback`, `POST /api/apps/{app}/stop`(모든 슬롯 0), `POST /api/apps/{app}/start`, `DELETE /api/apps/{app}?database=`(`true`면 DB도 DROP). 셋 다 배포 Lease를 잡고, 진행 중이면 409 |
| lily-builder | 온프레미스 에이전트 | WebSocket `/api/agents/connect?token=`. 잡은 `type=job`. 롤백은 `type=rollback`, 거점 전환은 `type=home`, 그 취소는 `type=home-cancel`, 버스팅 설정은 `type=burst`. 에이전트는 3초마다 `burst-state`로 상태를 보고한다 |
| lily-cicd | lily-db-provisioner | `GET /api/databases?projectId=`, `POST /api/databases`, `GET /api/databases/{id}/env`. `projectId`는 `appName` |
| lily-builder | lily-db-provisioner | `GET /api/databases/{id}/env?host=&port=`. 입구는 `POST /api/burst/apps/{app}/database` |
| lily-on-premise | lily-builder | `POST /api/burst/apps/{app}/standby`, `GET /api/burst/builds/{id}`, `GET /api/burst/apps/{app}`, `PUT /api/burst/apps/{app}/replicas`. 플랫폼 연결이면 같은 method·path를 소켓 `type=burst`로 보낸다 |
| lily-builder | 엣지 Worker 관리 주소 | `PUT https://lily-edge-queue.{zone}/apps/{host}/queue/config` 본문 `{ gcpPercent }`. 앱 DO 설정 `split` 이 있으면 Worker 가 `{app}-gcp`·`{app}-aws` 로 나눈다 |
| lily-builder | Cloudflare | `EdgeWorker`. `PLATFORM_EDGE_ENABLED`이면 기동할 때 `PUT /accounts/{account}/workers/scripts/lily-edge`. 대기 배포가 끝난 앱에 `POST /zones/{zone}/workers/routes`(`{app}.lilycloud.kr/*`)와 `{app}-cloud` 프록시 CNAME(→ ALB). 앱을 지우면 둘 다 지운다 |
| lily-builder 프로세스 | Claude 또는 OpenAI | `AiAdvisor`. 설정 키 분류와 실패 진단. `ANTHROPIC_API_KEY`가 있으면 Claude, 없고 `OPENAI_API_KEY`가 있으면 OpenAI. 둘 다 없으면 호출하지 않고 규칙을 쓴다 |
| lily-observer | lily-frontend | `RemediateWatch`가 `WATCH_INTERVAL`(기본 30초)마다 상태 판정을 한다. CRITICAL이 `JUDGE_CONSECUTIVE`(기본 2)번 연속이고 `observer.remediate.enabled`이면 CloudWatch 최근 15분을 읽어 `POST {REMEDIATE_FRONTEND_URL}/api/internal/remediate`. `POST /api/apps/{app}/remediate`도 같은 전송이다. 롤백은 부르지 않는다 |
| lily-frontend | lily-builder | `POST /api/remediate/drafts`. 배포 커밋의 해당 파일, 가린 로그, 설치 토큰 |
| lily-builder | lily-jev | `lily.remediate.enabled`이고 `JEV_API_KEY`가 있을 때 `POST https://api.typesafe.ai/v1/systemone`. 질문 `code-defect`, 예 확률 0.8 이상만 diff로 간다. 키가 없으면 묻지 않고 코드 결함으로 본다 |
| lily-builder | Groq | `GROQ_API_KEY`가 있으면 `POST https://api.groq.com/openai/v1/chat/completions`, 모델 `openai/gpt-oss-20b`. 없으면 Claude, 그것도 없으면 OpenAI. diff만 돌려주고 GitHub는 호출하지 않는다 |

받는 컨트롤러: `BuildController`, `AgentController`, `DeployController`, `AppController`, `DatabaseController`, `AgentSocket`, `BurstController`, `RemediateController`.

`lily-observer`의 `GET /api/apps/...` 는 선언되어 있다. 이 사본의 다른 모듈에서 그 경로를 호출하는 코드는 없다.
